Basic Users

What is this and why does it exist?

Where Is My Money (WIMM) is a web application that allows you to keep track of your financial life (savings, expenses, transactions, investments, income) so you can have clarity on how you use your money.This application arose from the author's need to organize his personal finances in one place, independently of banking apps and the way he stores his money.

What problems does this application solve?

As its name suggests, it helps you determine how you use your money and allocate it to cover your goals. These features are useful when you need to plan to achieve financial objectives that exceed your income.

Who is this application not for?

This application requires organization, discipline, patience , and basic financial literacy. You need to record every financial transaction as accurately as possible for it to work. If you don't possess these qualities, the application won't be useful to you.

How to use it? (in 60 seconds)
  1. Register your user account.
  2. Go to "Settings" and personalize aspects of your user account.
  3. Go to "Accounts," create the necessary accounts to manage your money, as well as their corresponding budgets, goals, and descriptions.
  4. Go to "Transactions" and add the transactions. In this section, you can budget (distribute money from one account to others according to a proportion), as well as search for a specific transaction using the search function.
  5. Finally, the "Dashboard" displays a summary of the money you have in each account, the status of your goals, and graphs showing the evolution of each account over time.

What design decisions did the author make and why?

During the application's design, decisions focused on simplicity, scalability, and user experience were made. All of this was done taking into account the project's limitations.

  • Mobile First: This application was designed prioritizing mobile devices. This design addresses the fact that most users currently access content on this type of device, and the content must be legible without zooming or horizontal scrolling.
  • Replacing tables with expandable lists and panels: Initially, the use of tables to display information was considered, but lists and cards were chosen because they improve the user experience on small screens.
  • The design is scalable and ready to add features without requiring major redesigns.
What technology does the project use and why?

WIMM uses different technologies for its operation. The main ones are:

  • PostgreSQL
  • Django
  • Angular

This technology stack was carefully selected to meet the current and future needs of the project. The author made the selection based on their personal experience and research from various sources.

PostgreSQL is the database engine that was chosen due to its compatibility with the SQL standard, its open-source nature, and its good balance between performance, features, and resource consumption. Other alternatives considered were MariaDB, but this engine offers fewer features that will be used in the future of the project.

Django (and associated libraries, such as Django REST Framework) is the framework used for server-side development. Generally, Spring Boot is used in Spain, but the author decided to use Python and Django because in the future, this application will use functions related to Machine Learning and Artificial Intelligence. Python, the language Django uses, has a mature ecosystem that allows for easy integration of these features.

Other alternatives considered were Flask and FastAPI. The author discarded these options because Django offers a complete, mature ecosystem ready for developing the application. Although Django might be somewhat resource-intensive for a simple REST API application, the performance is acceptable.

Angular (and associated libraries, such as chart2-js) is the framework the author used for client-side development. Like Django, it offers a dogmatic philosophy that allows for easy code organization. It also has a complete ecosystem for developing single-page applications (SPAs) without having to make so many design decisions. It uses TypeScript, whose static typing facilitates finding and mitigating errors. Other alternatives considered were React, Vue, and Svelte. These options offer advantages such as faster learning curves, greater flexibility, and even better performance for a small project, but the author chose Angular because it offers greater future stability, code that can be maintained for longer, and project consistency.

What are the current limitations?
  • Paging needs to be implemented in the transactions view.
  • Data import and export capabilities.
  • Offline support capabilities. Not only should the interface be displayed, but the user should have the option to save their data on the device, without needing to do it on a server. A more private option.
  • The ability for a user to manage different currencies in their account.
  • Incorporating machine learning tools to predict the future behavior of an account. This would help answer questions like: "If things continue this way, when will I achieve this goal?"
  • The ability to input data using optical recognition of tickets or invoices.
What did you learn building the application?
  • The author uses Django features such as Subqueries, outerRef, and cached properties to avoid making repetitive (and costly) calls to the database.
  • User Interface design using the Mobile First methodology.
  • In this application, I used the Model, Data Service, Business Service, and Component architecture within Angular, as well as a way to structure several applications within a single project to reuse code.
  • It is worth mentioning that, in this application, the author found it necessary to adapt each Data Service component, since not all of them possess full CRUD functionality and some require additional methods.
  • Use of styles that adapt to the type of device displaying them (media queries).
  • Use of styles that adapt to the theme of the device displaying them (light-dark).
  • The author learned that most of the business logic should be in the backend and that the frontend should only have the behavior related to how the information is displayed.
